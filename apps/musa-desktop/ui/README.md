# musa-ui

The desktop application's interface: the front end of the Tauri shell in `../src-tauri`, over `musa-project`. It also
runs standalone in a browser against the committed fixtures — that is how the engraving is reviewed and how the
screenshot goldens are taken. The difference is one check: without a shell answering, the session renders whatever
snapshot it was seeded with and every command is a no-op.

**`docs/interface/` governs this directory.** It is the design document, not a summary of the code: `00-thesis.md` (leaf
and margin, and what is rejected), `01-visual-language.md` (every token, the Compose layout), `02-engraving.md` (how
Verovio is driven, themed, and re-rendered), `03-interaction.md` (selection, keyboard, the accessibility floor),
`04-provenance.md` (Origin view), `05-states.md`, `06-performance.md`. If the code and those documents disagree, either
the code is wrong or the document needs a deliberate repair — never let them drift silently.

## Run it

```sh
npm install
npm run dev
```

Then <http://localhost:5173>. Query parameters, for review only:

| Parameter | Effect |
| --- | --- |
| `?score=counterpoint` | Show another fixture (`glass-mountain`, `counterpoint`, `twinkle`) |
| `?view=sheet` | Show it as engraving alone, with no chrome |
| `?theme=light` / `?theme=dark` | Pin a theme; without it the app follows the system |

## What is here

| Path | What lives there |
| --- | --- |
| `src/lib/design/` | The token file and the four bundled faces. The only place a colour, family, size, or duration is stated. |
| `src/lib/engrave/` | Verovio in a Web Worker, behind the `Engraver` interface. Nothing outside it touches a toolkit, an MEI string, or raw SVG. |
| `src/lib/score/` | The engraved page, the overlay layer, and the pointer model over both. |
| `src/lib/session/` | The session store, the one module that talks to Tauri, and the generated DTO types and command registry. |
| `src/lib/state/` | The shape `musa-project` serializes, and the selection model. |
| `src/lib/ui/` | Primitives — leaf, margin, typographic row, fraction, position, staff bracket, transport readout. |
| `src/screens/` | Compose, the launch state, and the chrome-free sheet the raster goldens photograph. |
| `fixtures/` | Real `ProjectSnapshot`s and the `.mei` of every fixture score, generated by tests in `musa-project`. |

The frontend computes nothing musical. Bar numbers, beats, pitch spellings, durations, and provenance all arrive in the
snapshot (`03-interaction.md` §7); if one is needed and absent, the snapshot gains a field.

## Tests

```sh
npm run check        # svelte-check
npm run test:unit    # sanitizer, token contrast, session store, in node
npm run test:screens # Playwright: screenshot goldens, selection, offline, session, budgets
npm run test         # both
```

The first Playwright run on a machine needs its browser:

```sh
npx playwright install chromium
```

### Updating the goldens

`tests/__screenshots__/` is the design's regression net for the rest of the sequence. It holds two kinds of golden:
the raster images — Playwright screenshots at 2×, with the tolerance stated in `playwright.config.ts`, rather than a
`resvg` rasterization, so that what is compared is what a browser actually draws — and the `*-structure.txt` digests
of what each page is made of. The images catch a design regression; the digests say what changed in words.

Regenerate only when a change to the design is intended, and read every file the run rewrites:

```sh
npm run screens:update
```

### The generated types

`src/lib/session/generated/` is written by `cargo test -p musa-desktop` from the Rust DTOs and the command registry, so
the bridge and the menu cannot drift from the interface. If it goes stale the Rust test fails; regenerate with:

```sh
UPDATE_UI_FIXTURES=1 cargo nextest run -p musa-desktop
```

### The fixtures

Every file in `fixtures/` is written by a test in `crates/musa-project`, so none of them can drift from the types they
serialize. The large-score pair — `large-score.mei` and `large-score.snapshot.json` — is the 100-bar, four-part
workload the performance budgets are measured on; its source, `tests/fixtures/large-score.musa` at the repository
root, is generated from a rule by the same test rather than written by hand. If a fixture goes stale the Rust test fails; regenerate with:

```sh
UPDATE_UI_FIXTURES=1 cargo nextest run -p musa-project
```
