# One piece, several descriptions

**Status: retained comparison model; rejected as Musa's execution core. These notes do not set Musa's rules.**

[The core-calculus research](../core-calculus/00-what-the-calculus-must-explain.md) found that this model answers a
comparison question, not the execution question. `Description`, `Event`, and `Match` can still help ask whether a
performance fits a score or recording. They do not explain how to build a passage, schedule its events, connect an
instrument, or run sound. The rejected proposal stays here beside that finding.

Musa currently builds notation, performance data, and audio in that order. Earlier design work mistook this useful build
order for a fact about music.

This research asks a simpler question:

> How can a written passage, a studio setup, a performance, and recorded sound describe the same music without being
> treated as the same thing?

The candidate answer is that each description places requirements on how the music may be played or produced. A
performance is one event that meets those requirements. A recording tells us something about an event and may later
become material for another one. This may be useful for comparison and analysis; it is not the selected core calculus.

## Reading order

1. [One piece can have several descriptions](00-one-piece-several-descriptions.md) tests the idea against Bach and
   figured bass, Sibelius's Fifth Symphony, Goldfrapp's “Ooh La La,” and two hard edge cases. It states the few rules
   that all three examples support and explains what they would change in Musa.
