# Interface Prototype: the design, before any plumbing

## Task

Build the Compose workspace's **look and engraving** as a standalone Svelte app driven by committed fixtures — real
Verovio, real Bravura, real design tokens, both themes, no Tauri and no IPC. This prompt exists so the interface's
quality is settled and reviewable *before* a single command is wired, instead of being whatever falls out of the
plumbing. If the screenshots this prompt produces are not something a composer would want to look at for three hours,
nothing later in the sequence fixes that.

## Read

- **`docs/interface/`** in full — it is the governing document for prompts 20–26. In particular `00-thesis.md` (leaf and
  margin; what is rejected), `01-visual-language.md` (every token; the Compose layout), `02-engraving.md` §§1–5, §9.
- **`docs/interface/prototype.html`** — open it in a browser first. It is the static reference mockup of exactly this
  screen, with real Verovio output, and it already answers the questions that would otherwise be guessed: overlay
  geometry in staff spaces, the `currentColor` sanitizer, the parts bracket, the Origin tint. Rebuild it properly here;
  do not port its markup.
- Roadmap §14.1–§14.4 (architecture this design implements), §14.8 (zero setup — everything bundled).
- Prompt 13's `xml:id` contract; prompt 19's `ProjectSnapshot` shape (the fixture must be a faithful serialization of
  it, not an invented shape).

## Design

- Create `apps/musa-desktop/ui` as a Vite + Svelte 5 + TypeScript app. **No `src-tauri` yet** (prompt 21). It runs under
  `npm run dev` in a browser.
- **The snapshot must carry the musical facts the screen shows.** `03-interaction.md` §7 forbids the frontend from
  computing bar numbers, beats, pitch names, or provenance, and prompt 19's `ProjectSnapshot` carried none of them. Add
  `ScoreFacts` to `musa-project` — title, tempo, key, meter, parts and voices, and one `EventFacts` per event (engraved
  `xml:id`, part, voice, spelled pitch, exact duration, `bar`/`beat` as exact fractions, and the origin path) — derived
  once per successful compile. This is the field the design said the snapshot would gain.
- **Fixtures, not mocks.** Commit under `apps/musa-desktop/ui/fixtures/`:
  - `glass-mountain.snapshot.json` — a real `ProjectSnapshot` serialized by a small `#[test]` in `musa-project` that
    writes it (so the fixture cannot drift from the type);
  - `glass-mountain.mei`, `counterpoint.mei`, `twinkle.mei` — generated by `musa render --to mei`;
  - a large-score fixture is prompt 22's concern, not this one.
- **Design tokens** in `src/lib/design/tokens.css`, exactly the values in `01-visual-language.md` §2–§6, with the dark
  set under both `@media (prefers-color-scheme: dark)` and `:root[data-theme="dark"]`. A hex literal or font name
  anywhere else in the UI fails review.
- **Fonts bundled** as woff2 in `src/lib/design/fonts/`: Bravura, Academico (both from the Verovio distribution),
  Instrument Sans, Recursive Mono Linear. `@font-face` with `font-display: block` for Bravura (a fallback glyph in a
  score is worse than a blank frame). No network requests at runtime — assert this in the smoke test.
- **Primitives** in `src/lib/ui/`, each doing one job: `Leaf`, `Margin`, `TypographicRow` (label + value, hairline on
  focus), `Fraction` (true diagonal fraction, `01-visual-language.md` §3), `Position` (`bar:beat`, bar dominant),
  `PartBracket` (the real staff bracket for the parts list), `TransportReadout`, `GlyphButton` (SMuFL glyph + accessible
  name, no icon font of our own).
- **Engraver module** in `src/lib/engrave/` behind the `Engraver` interface of `02-engraving.md` §1, already running in
  a Web Worker with a persistent toolkit and generation tokens. Layout options exactly as `02-engraving.md` §4. The
  `currentColor` sanitizer (§3) is implemented here and unit-tested — dark mode must re-ink, not filter.
- **The screen**: the Compose layout of `01-visual-language.md` §7, static. Transport is present and disabled. Parts
  list is bracketed and real. Inspector shows the first event's rows including the Origin row of `04-provenance.md` §3.
  Selection and hover **are** implemented (they are pure frontend, `03-interaction.md` §2) so the overlay layer and
  staff-space units are proven here; the playhead, keyboard map, and Origin view are not.
- **Screenshot goldens** via Playwright: Compose at 1440×900 and 1100×720, light and dark, plus each MEI fixture's first
  page rasterized per `02-engraving.md` §9. Committed under `apps/musa-desktop/ui/tests/__screenshots__/`. These are the
  design's regression net for the rest of the sequence.

## Target

- `apps/musa-desktop/ui/` — Vite/Svelte/TS app, tokens, bundled fonts, primitives, worker-based engraver, static Compose
  screen, fixtures.
- `crates/musa-project`: one test that writes `glass-mountain.snapshot.json` to the fixtures directory (guarded so CI
  fails when the committed fixture is stale).
- Tests: token contrast test over `tokens.css` (`01-visual-language.md` §2); sanitizer unit tests; Playwright screenshot
  goldens (light/dark, two sizes); a no-network assertion.
- `apps/musa-desktop/ui/README.md`: how to run, how to update goldens, and the rule that `docs/interface/` governs.

## Check

```sh
cargo nextest run -p musa-project
cargo fmt --check
cd apps/musa-desktop/ui && npm ci && npm run check && npm run test && npm run build
cd apps/musa-desktop/ui && npm run dev   # review: light and dark, 1440 and 1100, zoom 50–203 %
```

Review gate before the prompt is `done`: the four committed screenshots are attached to the commit message or the PR,
and the reviewer confirms the leaf-and-margin thesis is visibly true — no panel boxes, one shadow, no icon toolbar.

Commit as `Add desktop interface prototype and design system`.

## Stop

- No Tauri, no `src-tauri`, no IPC, no Rust command surface (prompt 21).
- No playback, no playhead, no transport behavior (prompt 23).
- No keyboard map beyond focus and arrow navigation of the parts list (prompt 23).
- No Origin view interaction — only the inspector's Origin row (prompt 24).
- No editing of any kind (prompts 25, 26).
- No page virtualization, no zoom re-layout beyond the discrete steps, no long-score work (prompt 22).
