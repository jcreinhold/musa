# Source and provenance

The `.musa` source is canonical. Score and studio UIs are structured editors of that text: no second editable AST, no
mutable expanded cache. Anything the interface can do, the language can say.

## The semantic quotient

Compilation elaborates the rich surface structure — motifs, repeats, transforms — down to the temporal kernel. That
elaboration is a quotient: it forgets how the facts were produced and keeps only what they are. Two passages that
elaborate to the same track are the same music, whether one was typed out note by note and the other generated by a
canon.

Forgetting is the point. Backends read one normalized track and never re-implement motif expansion. But forgetting must
not destroy: the kernel is a quotient *of* the source, and the mapping back is preserved alongside it.

## Provenance

Every compiled fact carries an `Origin`: the source span it came from, and the expansion path — through which motif
uses, which transforms — it took to arrive. This is recorded exactly, not approximated.

Provenance answers the question a composer working with transformed material asks constantly: *where did this come from,
and what happens if I change it?* It powers:

- **go-to-definition** in the language server, from a generated note to the construct that produced it;
- **Origin view** in the desktop app, where authored and generated music read differently on the page;
- **the editing choice**: changing a generated note must offer a real choice between editing the motif definition —
  which moves every use — and detaching this one occurrence into authored music.

## The exports keep the thread

The MEI export emits stable `xml:id`s that trace each engraved note back to its origin. That is what lets the desktop
app hover a note on the page and highlight its source: the thread from text to track to page is never cut.
