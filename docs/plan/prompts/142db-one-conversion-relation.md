# One Conversion Relation, Modulo the Index Theory

## Task

`02-core-calculus.md` §3 and §1.5 describe **two** equalities: "There are two deciders and they are independent... and
neither calls the other." That is a true statement about the implementation promoted into the specification, and it is
why a reader meets the index stratum as a second equality bolted beside the first rather than as part of the one Musa
has. State the relation that is actually there — `≡` is the congruence generated by β, η, δ, ι **together with** the
index theory `T`, decided by normalization by evaluation with a decision procedure at index sort — fix the conversion
strategy normatively while the section is open, and rename `Shape::Refine` to `Shape::Indexed`, because a mechanism with
no subtyping and no predicate over the inhabitant is indexing and not refinement.

## Read

- `docs/rules/language/02-core-calculus.md` §3's paragraph beginning "**An index is not decided here**", and §1.5's
  "**Conversion asks the solver**". These are the two passages this prompt rewrites, and they are the only two.
- Strub, *Coq Modulo Theory* (CSL 2010), and Blanqui's rewriting-modulo line. Conversion extended by a decidable
  first-order theory, with subject reduction and decidability of type checking preserved. This is the existing
  metatheory for the thing Musa built, and citing it replaces an architecture asserted in prose with one that has a
  proof somewhere.
- Xi and Pfenning (1999) and Xi (2007), already at `docs/rules/language/citations.md:242`. The stratification and the
  erasure are theirs; what this prompt adds is the statement that the two procedures compose into one relation.
- Freeman and Pfenning (1991), *Refinement types for ML*, and the Liquid Types line — read for the classification this
  prompt **refuses**. A refinement type is a subset carved by a predicate over the inhabitant and it lives on subtyping.
  `crates/musa-calculus/src/lib.rs:57` records that Musa has no subtyping; `term.rs`'s doc on `Refine` records that "a
  refinement never agrees with a bare type, because `Row(12)` and `Row` are two types". Invariance plus a parameter
  beside the type is indexing. The name is the last thing still claiming otherwise.
- `crates/musa-calculus/src/convert.rs`, `Conversion::folded` — rigid heads compared before either side is unfolded, one
  side opened at a time. This is Lean 4's `isDefEq` strategy and it is implemented and unstated.
- `crates/musa-calculus/src/term.rs`, `Shape::Numeral` — a closed value of a counting family compared as a count rather
  than as a tower. This is Idris 2's `%builtin Natural` and it is implemented and unstated.
- `crates/musa-calculus/src/family/mod.rs:14-19` — "There are **no indices**", and the sentence naming index unification
  inside the conversion checker as "where the complexity of a general indexed family lives". And `:74-76`, which admits
  **large elimination**. The first is why Musa's conversion is cheap; the second is the one case in which it runs user
  code, and neither is stated in §3.
- `docs/rules/language/10-traits.md` §7, which tells a reader to hold two equalities apart and does not mention the
  index theory at all.
- `docs/rules/README.md`, *Changing a decision*, and `constitution.md` §9. This prompt is **not** an amendment — see the
  last Stop item — and the worker should be able to say why.

## Design

**One relation, stated once.** §3's judgment becomes:

```text
Γ ⊢ A ≡ B   is the congruence generated by  β, η, δ, ι  ∪  T
```

where `T` is §1.5's index theory. It is decided by NbE, whose index-sort case consults `T` rather than normalizing —
because an index is not a term and cannot be evaluated. `T` is decidable, therefore `≡` is decidable, therefore type
checking is. That is the same dependency chain §3 already draws, with the index stratum inside it rather than beside it.

Nothing about the code changes here. `index.rs` still does not import `value.rs`, the two procedures are still separate,
and the separation is still the reason the term core did not grow. What changes is that a reader is told about **one
relation with two decision procedures** instead of two relations — which is what makes the stratum read as part of the
design rather than as a second mechanism.

**`≡` is an equivalence relation, and reflexivity is now true.** 142da is a dependency for exactly this reason: §3
cannot state that `≡` is reflexive while `Row(mystery n)` is inconvertible with itself. State the three properties, and
state where each is discharged — α on read-back for the term part, and `T`'s own reflexivity for the index part.

**The strategy is normative, not incidental.** Four decisions keep conversion cheap, all four are implemented, and none
is written down, so a refactor can lose one and nothing fails. §3 gains them as rules:

- **Rigid heads first.** Two neutrals with different rigid heads are different without unfolding either.
- **One side at a time.** When a head must be unfolded, one side is opened and the comparison retried, never both.
- **A numeral is compared as a number.** A closed value of a counting family is never expanded into a tower.
- **The meter is the backstop, and a crossing is a refusal.** Never a hang, and never a silent pass.

**Name the one case where conversion runs user code.** Three of the four cost sources in dependent conversion are absent
from Musa by construction, and §3 should say so because each absence is load-bearing: index unification inside the
checker is absent (§1.1 admits no family indices); unary towers are absent (numerals); unfolding proof terms is absent
(there are none, which is what Coq's `Qed` and `Opaque` exist for). What remains is **large elimination** — a recursor
whose motive is a type — which is genuine type-level computation bounded by §2.4's structural recursion and by the
meter. Naming it is what makes the other three absences a claim rather than an accident.

**`Shape::Refine` becomes `Shape::Indexed`.** `RawShape::Refine`, `Raw::refine`, `refinement_shown`, and the `refined`
test helpers move with it. This is behaviour-preserving and must be a pure rename: no arm gains or loses a case. §1.5's
prose already says "index" everywhere it matters; the code is what still says "refinement", and this repo's law is that
the two agree.

**`10-traits.md` §7 gains the third thing.** It currently names definitional equality and `Eq<A>.equal`. After this
prompt it names three: conversion, the index theory as the part of conversion that decides indices, and `Eq<A>.equal` as
a computation over values. The distinction §7 exists to draw is unchanged; it is just complete.

## Stop

- **No subtyping**, and no coercion between an indexed type and the type it indexes. `Row(12)` is not a `Row`, and this
  prompt states that classification rather than changing it.
- **No change to §1.5's grammar**, to the index domain, or to `index::decide`. `T` is what 142c decided and 142d built.
- No second decision procedure, no SMT, no constraint accumulation, and no entailment beyond the equality of two linear
  forms the corpus generates.
- No identity type, no proof term, no `refl`, no `J`. §1.4 stays as it is and this prompt gives no evidence to re-open
  it.
- No `law` clause and no trait-carried algebraic claim. 142e settles that, and settles it in the negative.
- The rename changes no behaviour. If a test needs editing for anything but a name, stop — that is a semantic change
  hiding in a refactor.
- **This is not an amendment under `docs/rules/README.md`.** `constitution.md` §9's answers are untouched: no identity
  type, no index unification, no proof terms, no dependent motive, no universe polymorphism. `02-core-calculus.md` is
  candidate under the precedence ladder, and what changes there is how one already-decided architecture is stated. If an
  edit turns out to change one of §9's nine answers rather than restate §3, **stop and raise it** rather than writing
  it.
