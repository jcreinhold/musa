# The Elaboration Language in the Workbench

## Task

Make score functions, templates, modules, theory assertions, and analyses legible in the desktop workbench without
turning the application into a visual programming system or adding a second semantic model. A musician should be able to
ask what a term means, where generated music came from, and why an advisory finding was reported; a language implementor
should see the same types, definitions, source maps, and evidence that the compiler exposes through prompt 122. The
existing Sound and Mix workspaces remain usable but are not redesigned here; prompt 188 integrates the later
instrument/control/asset model through the same source-edit and immutable-fact boundaries.

## Read

- `docs/rules/desktop/`, especially the one-selection model, Origin view, states and voice, and performance budgets.
- Prompts 23–26, 52–56, and 76 for score/source linking, structured edits, diagnostics, and realization evidence.
- `docs/rules/language/01-surface.md`, `04-templates-and-modules.md`, and `07-analysis.md`.
- Prompt 122's compiler/project fact boundary and LSP behavior; the desktop is another consumer of that boundary.

## Design

Preserve the source as canonical and the score as a projection. Extend the existing Source and Origin workspaces rather
than adding a graph canvas, inspector dashboard, or mutable expanded AST.

Required interactions:

- hover and completion in Source show the compiler's inferred type, declared signature, named/default parameters, and
  short musician-facing documentation; implementation details remain available through a deliberate “language detail”
  disclosure, not in the first sentence;
- selecting music generated by a function, template, module application, assertion, or events quote extends Origin's
  existing chain with definition, call/instance, argument/hole, and occurrence steps. Shared or plural origins remain
  plural rather than choosing one convenient source span;
- definition, references, and read-only standard-library navigation use prompt 122's recorded facts. Bundled sources are
  visibly library material and never masquerade as editable project text;
- an explicit assertion is shown at its written location and may offer the compiler's certain source fix. Advisory
  analysis appears as findings with scope, strength, evidence, and alternatives; it never paints the score as though a
  debatable theoretical reading were a syntax error;
- events documents and quoted regions have a distinct, plainly labelled interchange/raw state. Score gestures may
  navigate to their origin but may not synthesize edits inside quoted or included event track facts;
- the existing command palette may insert documented declaration skeletons or explicit arguments. It inserts text and
  lets the normal compiler validate it; it does not construct hidden nodes.

Write the wording and interaction rules into `docs/rules/desktop/` before wiring them. The musician-facing path uses
terms such as “scale degree”, “voicing”, “generated here”, and “possible cadence”. A secondary developer path may name
`Music`, signatures, source maps, and elaboration budgets. Both descriptions are projections of one fact rather than
independently computed explanations.

Keep update cost inside the existing budgets. Source keystrokes retain B1 behavior; semantic results are revision-tagged
and may use the last valid artifact; expanding an Origin chain or analysis finding must not trigger recompilation.

## Target

- Governing additions to `docs/rules/desktop/` for elaboration constructs, evidence, raw-event track states, wording,
  keyboard access, and empty/loading/stale/error states.
- `apps/musa-desktop/ui`: Source affordances, Origin-chain extensions, standard-library documents, analysis findings,
  assertion fixes, and accessible keyboard/focus behavior.
- The minimal Tauri/project command wiring needed to consume prompt 122's immutable facts; no compiler internals cross
  the boundary.
- Unit and Playwright coverage for singular/plural origin, stale results, an ambiguous analysis, a failed assertion, a
  generated standard-library term, an events quote, keyboard-only use, and screen-reader names.
- Screenshot goldens at narrow and wide sizes using representative real `.musa` fixtures rather than isolated mocks.

Plus a recorded manual pass: define and apply a transposing voice template, follow one generated note through Origin,
open its bundled pitch operation, inspect an ambiguous cadence report, and apply one certain assertion fix entirely by
keyboard. Commit as `Make elaboration legible in the workbench`.

## Stop

- No node graph, visual programming language, property-grid AST editor, or second type/theory engine in TypeScript.
- No direct score edit of generated, included, quoted, or analysis-derived facts; navigate to editable source instead.
- No automatic acceptance of an advisory analysis and no red-error styling for contestable theoretical judgments.
- No new layout or animation work unrelated to understanding the elaboration language.
- No audio graph redesign, instrument browser, asset browser, or sound-control model — prompt 188 owns that work after
  the audio semantics exist.
